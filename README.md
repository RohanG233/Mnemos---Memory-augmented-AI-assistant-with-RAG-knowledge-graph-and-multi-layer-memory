## 1. What Is Mnemos?

Mnemos is a memory-augmented AI assistant that remembers you.

Unlike a stateless chat interface, Mnemos maintains:

- **Semantic memory** — personal facts, preferences, and stable information you share
- **Episodic memory** — meaningful decisions and milestones from your conversations
- **Procedural memory** — instructions for how the assistant should behave
- **Short-term conversation context** — the current session's rolling window
- **Document knowledge** — text files you upload, chunked and indexed for retrieval
- **Knowledge graph** — entities and relationships extracted from your documents and conversations

Every response is generated by combining the most relevant pieces from all these memory layers with the current query, then passing the assembled context to the LLM.

## 4. Feature Breakdown

### Authentication

- Google OAuth 2.0 via `requests-oauthlib`
- Short-lived JWT access tokens (15 min, Bearer header)
- Long-lived refresh tokens (7 days, HttpOnly `SameSite=None; Secure` cookie)
- Automatic token rotation on every refresh
- Silent refresh on page load via `AuthContext`
- All protected endpoints require a valid `Authorization: Bearer <token>` header
- Every database query includes `user_id` — users cannot access each other's data

### Chat & Conversations

- Conversations are created server-side (`POST /chat/conversations`)
- The server-assigned `conversation_id` is stored in the room and sent with every message
- Messages are persisted to MongoDB after each exchange
- Short-term rolling context window (6 message pairs) kept in-process
- All conversation history survives restarts via MongoDB

### RAG Pipeline

```
User query
  → BM25 search (per-user corpus, in-process index)
  → Vector search (ChromaDB, user_id filtered)
  → Merge unique chunks from both (deduplicated, top-5)
  → Graph retrieval (ego-graph from entities found in query)
  → Memory retrieval (semantic + episodic + procedural, ChromaDB)
  → Build system prompt with all context
  → Send to Ollama LLM
  → Return answer
  → [background] update graph + memories
```

### Memory System

| Type | Trigger | Storage |
|---|---|---|
| Semantic | Personal facts / preferences | ChromaDB `memory` collection |
| Episodic | Significant decisions / milestones | ChromaDB `episodes` collection |
| Procedural | Behavioural instructions | ChromaDB `procedures` collection |
| Short-term | Last N message pairs | In-process `ConversationMemory` |

Memory decay: an importance × recency × usage score is computed on retrieval. Memories below the forget threshold are deleted.

### Knowledge Graph

- LLM extracts subject–relation–object triples from every document chunk and chat message
- Triples are stored as a directed multigraph (NetworkX) serialised to JSON per user
- At query time, entities mentioned in the query are found in the graph and their 2-hop neighbourhoods are retrieved
- Graph is written atomically (tmp file → rename) to prevent corruption

### Document Ingestion

1. Upload `.txt` file (max 10 MB, UTF-8)
2. Split into 500-character chunks with 70-character overlap
3. Embed with `sentence-transformers/all-MiniLM-L6-v2` → store in ChromaDB
4. Add chunks to per-user BM25 index
5. Extract knowledge graph triples from each chunk → save graph
6. Document ID returned — use it to delete the document later

## 6. Local Development

### Prerequisites

| Tool | Version | Purpose |
|---|---|---|
| Python | 3.11.x | Backend runtime |
| Node.js | 20+ | Frontend build |
| Ollama | any | Local LLM inference |

| Google Cloud account | — | OAuth credentials |

### Backend Setup

```bash
cd backend

# Create and activate virtual environment
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

# Install dependencies
pip install -r requirements.txt

# Create your .env file
cp .env.example .env
# Edit .env and fill in your values
```

### Ollama Setup

```bash
# Start Ollama (keep this terminal open)
ollama serve

# Pull the model (one-time, ~500 MB)
ollama pull hf.co/bartowski/Llama-3.2-1B-Instruct-GGUF:latest

# Verify it's available
ollama list
```

### Frontend Setup

```bash
cd frontend

# Install dependencies
npm install

# Create your .env file
cp .env.example .env
# Default VITE_API_URL=http://localhost:8000 is correct for local dev
```

### Running Everything

Open three terminals:

**Terminal 1 — Ollama**
```bash
ollama serve
```

**Terminal 2 — Backend**
```bash
cd backend
.venv\Scripts\activate   # or source .venv/bin/activate
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

**Terminal 3 — Frontend**
```bash
cd frontend
npm run dev
```

Open `http://localhost:5173` in your browser.

## 8. Render Deployment

### Step 1 — Prepare credentials

Before doing anything on Render, have these ready:

**MongoDB Atlas**
1. Log in at [mongodb.com/atlas](https://cloud.mongodb.com)
2. Create a free cluster if you don't have one
3. Database Access → Add Database User → copy username + password
4. Network Access → Add IP Address → `0.0.0.0/0` (allow all — Render uses dynamic IPs)
5. Connect → Drivers → copy the connection string
6. Replace `<password>` in the string with your actual password

**JWT secret**
```bash
python -c "import secrets; print(secrets.token_hex(32))"
```
Copy the output. You will paste it into Render.

**Google OAuth**
1. Go to [console.cloud.google.com](https://console.cloud.google.com)
2. Select or create a project
3. APIs & Services → OAuth consent screen → configure (External, test users if needed)
4. APIs & Services → Credentials → Create Credentials → OAuth 2.0 Client ID
5. Application type: **Web application**
6. Authorized redirect URIs: add `http://localhost:8000/auth/google/callback` for now (you'll add the production URL in Step 7)
7. Copy Client ID and Client Secret

### Step 6 — Configure Ollama on Render

Render web services do not natively host Ollama. You have three options:

**Option A — Run Ollama inside the backend service (recommended for demos)**

Requires Render Starter plan ($7/mo) for enough RAM.

1. Create `backend/start.sh`:
```bash
#!/bin/bash
set -e

# Install Ollama if not present
if ! command -v ollama &> /dev/null; then
  curl -fsSL https://ollama.com/install.sh | sh
fi

# Start Ollama in background, store models on persistent disk
export OLLAMA_MODELS=/data/ollama
ollama serve &

# Wait for Ollama to be ready (up to 60s)
echo "Waiting for Ollama..."
for i in $(seq 1 30); do
  if curl -sf http://localhost:11434/api/tags > /dev/null 2>&1; then
    echo "Ollama ready."
    break
  fi
  sleep 2
done

# Pull model only if not already cached on disk
MODEL="${LLM_MODEL:-hf.co/bartowski/Llama-3.2-1B-Instruct-GGUF:latest}"
if ! ollama list 2>/dev/null | grep -q "$MODEL"; then
  echo "Pulling model: $MODEL"
  OLLAMA_MODELS=/data/ollama ollama pull "$MODEL"
fi

# Start FastAPI
exec uvicorn app.main:app --host 0.0.0.0 --port "${PORT:-8000}" --workers 1
```

2. In Render dashboard → `mnemos-backend` → Settings → Start Command:
```
bash start.sh
```

3. Make sure the persistent disk is attached at `/data` (already configured in `render.yaml`).

**Option B — Separate VPS (most reliable)**

1. Rent a $5–10/mo VPS (DigitalOcean, Hetzner, Vultr)
2. On the VPS:
```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama serve &
ollama pull hf.co/bartowski/Llama-3.2-1B-Instruct-GGUF:latest
```
3. Open port 11434 only to Render's IP range (or use a VPN/tunnel)
4. Set `OLLAMA_URL=http://<vps-ip>:11434/api/chat` in Render

**Option C — No Ollama (graceful degradation)**

The app starts and all features work except chat generation.
Chat returns HTTP 503: "The AI model is currently unavailable."
Auth, documents, memories, and graph browsing all continue to work.

## 10. Persistence on Render

| Data | Storage | Survives restart? | Notes |
|---|---|---|---|
| Users, conversations, messages | MongoDB Atlas | ✅ Always | Cloud-hosted |
| Document chunks (vector) | ChromaDB on Render disk | ✅ With paid disk | Wiped on free tier |
| Knowledge graph (JSON) | Render disk | ✅ With paid disk | Wiped on free tier |
| BM25 index | In-process memory | ❌ Rebuilt at startup | Rebuilt from ChromaDB |
| Short-term conversation window | In-process memory | ❌ Lost on restart | MongoDB history still present |

## 12. Known Limitations

1. **Ollama on Render free tier is not practical** — 512 MB RAM is insufficient for any useful LLM model. Minimum Render Starter ($7/mo).

2. **ChromaDB and graph files require a persistent disk** — free tier storage is ephemeral. Upgrade to Render Starter and attach a 1 GB disk.

3. **Graph extraction is LLM-dependent** — uploading a document triggers one LLM call per sentence for triple extraction. This is slow for large documents and fails gracefully if Ollama is unavailable.

4. **Short-term memory is in-process** — the rolling conversation window is lost on restart. Durable conversation history is in MongoDB and can be reloaded.

5. **BM25 index is rebuilt at startup** — from ChromaDB data. Requires ChromaDB to be persistent for documents to be searchable after restart.

6. **Single worker** — `--workers 1` is set because the in-process BM25 index and short-term memory are not shared across processes. For horizontal scaling, these would need to be externalised.

## 13. Security Notes

- Never commit `.env` files — they are in `.gitignore`
- Rotate the `JWT_SECRET_KEY` if it was ever exposed
- Regenerate the Google OAuth client secret if it was ever exposed
- Change the MongoDB password if it was ever exposed
- Refresh tokens are stored as HttpOnly, Secure, SameSite=None cookies — not accessible to JavaScript
- All resource queries filter by `user_id` — user data isolation is enforced at the database level
- Uploaded filenames are sanitised against path traversal attacks
- File uploads are limited to 10 MB and `.txt` only
- API errors do not expose Python tracebacks to clients
